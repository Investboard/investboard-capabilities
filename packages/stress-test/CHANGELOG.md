# Changelog

## 0.3.0 (unreleased)

- Crypto takes the scenario's shares figure where a scenario names no crypto figure. Nine built-in scenarios (`gfc_2008`, `dotcom_2000`, `black_monday_1987`, `gulf_war_1990`, `bond_massacre_1994`, `asian_crisis_1997`, `russia_ltcm_1998`, `september_2001`, `euro_crisis_2011`) carried a crypto figure of 0 that was not a measured move (crypto did not exist in eight of those windows); they now name none and say so in their methodology. In `gfc_2008`, EUR 10,000 of crypto now ends at EUR 4,300 (the -0.57 shares figure) instead of staying at EUR 10,000. The stand-in is reported as `asset_class_default`, a scenario assumption, never direct history. The six scenarios with their own crypto move keep it, and a crypto figure a scenario names is always read first.
- Result for the rest: when one or more holdings cannot be modeled (an asset class with no figure or stand-in, or an economic currency with no scenario move), the result keeps every holding that can be modeled, sets `status: "partial"` with the reason `unmodeled_holdings_excluded`, and lists each holding left out in the new optional `calculation.excludedHoldings` with its value and reason (`asset_class_not_modeled` or `currency_not_modeled`). Totals, fractions and attribution describe the modeled holdings. Only a request with nothing to model is `unavailable`. Previously any unmodeled holding made the whole request `unavailable`.
- Reporting currencies: `baseCurrency` accepts GBP, CHF and JPY besides EUR and USD, using the existing cross-rate rule against the euro. A custom scenario without a move for the chosen currency returns `unavailable` with `unsupported_base_currency`; any other code still raises `StressInputError`.
- The calculation methodology becomes `whole-wealth-currency-replay-v6`, pinned by new evaluations. Snapshots saved as `whole-wealth-currency-replay-v5` replay under the v5 rules (no crypto stand-in, EUR or USD only, `unavailable` when any holding cannot be modeled) and return the result they were saved with. To apply the new rules, evaluate `snapshot.request` again and store the new snapshot.

## 0.2.0 (unreleased)

- Correct the built-in currency moves. In the ten scenarios since 1999 (`gfc_2008`, `covid_2020`, `rate_hike_2022`, `euro_crisis_2011`, `dotcom_2000`, `september_2001`, `china_shock_2015`, `q4_2018`, `banking_stress_2023`, `yen_carry_2024`), the USD, GBP, CHF and JPY `currencyShocks` are now each currency's move against the euro computed from the ECB euro foreign exchange reference rates on the window's first and last day (start rate / end rate - 1, rounded to two decimals). The earlier hand-entered figures pointed the wrong way in 8 of these 40 entries and were off by more than five points in 9 others. For example, `gfc_2008` USD changes from -0.08 to +0.12 (ECB 1.4037 on 2007-10-09, 1.2565 on 2009-03-09), so EUR 100 of USD cash with a EUR base now ends at EUR 112.00 instead of EUR 92.00.
- Each corrected scenario names the ECB source and records `provenance.currencyReviewedAt`. `ScenarioProvenance` gains this optional field and request validation accepts it as an ISO date. The five scenarios before 1999, the EUR entries, and all sector and asset-class figures are unchanged.
- The calculation methodology stays `whole-wealth-currency-replay-v5`. A snapshot contains its complete scenario, so snapshots saved with 0.1.0 replay with the figures they were saved with. To apply the corrected figures, evaluate the saved holdings again with the current built-in scenario and store the new snapshot.
- Rebuild from source during normal `npm pack` to keep packed JavaScript and declarations current.

## 0.1.0

Initial standalone source package with 15 historical scenarios, holding-level impacts, explicit economic-currency inputs, caller-supplied price and FX history, and JSON replay.
